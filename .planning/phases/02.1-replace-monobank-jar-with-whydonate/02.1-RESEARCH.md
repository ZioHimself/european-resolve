## WhyDonate Integration Model

### Widget Embed Mechanism

WhyDonate offers a donate button/form as an **HTML script embed** generated from their dashboard:

1. Log into WhyDonate dashboard → Donation Forms → Create Widget → select fundraiser
2. Style the widget (appearance, amounts, redirect URLs)
3. Copy the HTML script and paste into your website

The widget is **not an iframe** in the traditional sense — it's a JavaScript-powered embed that renders an inline donation form. Key capabilities:
- Handles full payment inline (donor doesn't leave the page)
- Supports 25+ payment methods (iDEAL, Bancontact, PayPal, Credit Card, Google Pay, Klarna, etc.)
- Powered by Stripe as payment processor
- Configurable redirect URLs after payment completion
- Pre-fillable amounts
- Multi-language support (18+ languages)

### Technical Integration Pattern

For a React/Next.js app with static export:
- The WhyDonate embed code is an HTML snippet (script tag) that needs to be injected into the DOM
- In React, this requires using `dangerouslySetInnerHTML` or dynamically creating script elements via `useEffect`
- Since the site is statically exported, the widget loads client-side only (which is fine — it's a payment widget)
- The embed code/URL should be stored as an environment variable (`WHYDONATE_WIDGET_URL`) and passed to the frontend at build time via `NEXT_PUBLIC_` prefix

### Redirect URL Configuration

WhyDonate allows configuring a **post-payment redirect URL** in the widget settings. This is the mechanism for payment confirmation:
- Widget redirects to: `https://european-resolve.org/events/2026-run-for-ukraine/register?token={TOKEN}&pid={PID}`
- The redirect URL can include query parameters that WhyDonate appends after payment
- This is configured in the WhyDonate dashboard, not programmatically

**Important limitation:** WhyDonate does not provide webhook callbacks or API notifications for completed payments. The redirect-based flow is the only integration mechanism available without Zapier.

## Payment Confirmation Architecture

### Secure Token Flow (D-07 through D-09)

```
Registration Flow:
1. User fills form → Frontend POSTs to backend
2. Backend: generates UUID payment_token, stores in Sheets row
3. Backend returns: { participantId, paymentToken, whydonateWidgetUrl }
4. Frontend: renders WhyDonate widget with locked amount
5. Widget configured to redirect to: /register?token={TOKEN}&pid={PID}

Confirmation Flow:
6. After payment, WhyDonate redirects to frontend with query params
7. Frontend reads token+pid from URL → POSTs to /api/register/confirm-payment
8. Backend: validates token (exists, matches pid, not already used)
9. Backend: marks row as "paid" in Sheets, records timestamp
10. Frontend: shows "Payment confirmed" state
```

### Token Security Considerations

- Token must be cryptographically random (use `crypto.randomUUID()` in Node.js)
- Single-use: once validated, the token is invalidated (prevents replay)
- Time-bound: optionally expire tokens after 24 hours (generous window for payment)
- The token correlates a specific registration to a specific payment completion
- **Not truly cryptographically secure against spoofing** — since WhyDonate doesn't sign the redirect, anyone who guesses or intercepts a token could fake a payment confirmation. Mitigation: tokens are random UUIDs (128 bits of entropy), one-time use, and the system is for a charity event (low-value fraud target)

### Google Sheets Schema Changes

Current columns (A–L): `participant_id, full_name, email, phone, tshirt_size, language, country, tier_id, amount_eur, gdpr_consent, comms_optin, registered_at`

New columns to add (M–P):
- `payment_token` (M) — UUID generated at registration
- `payment_status` (N) — "pending" | "paid"
- `paid_amount_eur` (O) — confirmed EUR amount (same as tier price)
- `paid_at` (P) — ISO timestamp when payment confirmed

## Technical Decisions

### WhyDonate Widget in React

Two approaches for embedding the WhyDonate HTML script in React:

**Option A: Link/Button approach (simpler)**
- Render a styled button/link that opens the WhyDonate donation page in a new tab or modal
- WhyDonate campaign page URL with pre-filled amount: `https://whydonate.com/en/fundraising/{campaign-slug}?amount={EUR}&currency=EUR`
- Post-payment redirect configured in WhyDonate dashboard settings
- Pros: simpler, no script injection, works with static export
- Cons: user leaves the page (or new tab), slightly worse UX

**Option B: Script injection (inline widget)**
- Dynamically inject WhyDonate's HTML embed script via `useEffect`
- Widget renders inline in the confirmation panel
- Pros: user stays on page, better UX
- Cons: more complex, potential CSP issues, script loading reliability

**Recommendation:** Start with **Option A** (link-based). The WhyDonate dashboard redirect URL configuration supports this well. The inline embed can be explored as an enhancement but adds complexity for a time-sensitive ("urgent") change. A well-styled CTA button with "Complete your donation" is clear and functional.

### Environment Variable Strategy

```
# Backend
WHYDONATE_WIDGET_URL=https://whydonate.com/en/fundraising/run-for-ukraine-2026

# Frontend (build-time via Next.js)
NEXT_PUBLIC_WHYDONATE_URL=https://whydonate.com/en/fundraising/run-for-ukraine-2026
```

The URL is the WhyDonate campaign page. Amount and redirect params are appended at render time.
