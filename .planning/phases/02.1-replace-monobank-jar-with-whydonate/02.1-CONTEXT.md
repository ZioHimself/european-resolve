# Phase 02.1: Replace Monobank jar with WhyDonate - Context

**Gathered:** 2026-07-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace all Monobank jar references with WhyDonate across frontend, backend, and planning docs. The post-registration confirmation panel embeds a WhyDonate donation widget (locked to the tier amount) instead of linking to Monobank. A secure one-time token flow confirms payment and marks the registration as "paid" in Google Sheets. All Monobank-specific messaging (Visa/Mastercard-only notices) is removed. Planning docs and requirements are updated to reflect WhyDonate as the donation provider. Google Sheets becomes the source of truth for progress data (sum of confirmed payments in EUR), eliminating Monobank API polling and UAH→EUR conversion.

</domain>

<decisions>
## Implementation Decisions

### WhyDonate Integration Model
- **D-01:** WhyDonate has no public REST API. Integration is via embeddable widget (HTML snippet from WhyDonate dashboard) or redirect link. No direct backend-to-WhyDonate API calls.
- **D-02:** Embed WhyDonate donation widget inline in the post-registration confirmation panel (replaces the old "Proceed to donate — Monobank" CTA button and Visa/Mastercard notice). Donors complete payment without leaving the page.
- **D-03:** Correlation via redirect callback — configure WhyDonate widget's post-payment redirect URL to include participant ID and a one-time payment token. No Zapier/webhook backend integration for Phase 02.1.

### Payment Scope
- **D-04:** WhyDonate handles tier payments only (€35/€75/€150 for Supporter/Champion/Patron). Fundraiser page donations (Track B) are a Phase 3 concern, but the plan is to use WhyDonate widget there too.
- **D-05:** Widget is pre-filled with the locked tier amount. Donor cannot modify the amount — only chooses a payment method.
- **D-06:** Remove all "Visa/Mastercard only" notices from the UI. WhyDonate widget natively shows available payment methods (iDEAL, Bancontact, PayPal, Credit Card, etc.). No custom payment-method messaging needed.

### Secure Payment Confirmation Flow
- **D-07:** Backend generates a unique, single-use payment token at registration time and stores it in the registration row in Google Sheets. This token is included in the WhyDonate redirect URL.
- **D-08:** After payment, WhyDonate redirects to the frontend with query params (token + participant ID). Frontend reads these, shows a "payment received" state, and POSTs to backend (`POST /api/register/confirm-payment` with `{token, pid}`).
- **D-09:** Backend validates the token (matches, not already used), marks the registration as "paid" in Google Sheets, records the confirmed amount, and invalidates the token. This prevents spoofed payment confirmations.

### Progress Data Source
- **D-10:** Google Sheets is the source of truth for progress data. The progress dashboard (Phase 3) sums confirmed (paid) registration amounts from Sheets. No external API polling (Monobank jar or WhyDonate) is needed.
- **D-11:** This eliminates the UAH→EUR conversion problem entirely — all amounts are stored in EUR natively.

### Downstream Cleanup
- **D-12:** Full cleanup in this phase — update all Monobank references in frontend code, backend code, requirements (REQUIREMENTS.md), project docs (PROJECT.md), and roadmap entries. Phase 3 planners start with a clean slate.
- **D-13:** Phase 3 fundraiser pages will also use embedded WhyDonate widget for donations (noted as a forward decision for Phase 3 planning).
- **D-14:** WhyDonate account/campaign is created manually by the organizing team. The campaign embed code / configuration is provided to developers as an environment variable.

## Existing Code Insights

### Reusable Assets
- `ConfirmationPanel.tsx`: Already has the CTA section structure — replace the `<a>` tag and Visa notice with WhyDonate widget embed
- `RegisterClient.tsx`: Has form submission logic — needs to handle the new payment token in the response and pass it to the WhyDonate widget
- `backend/src/routes/register.ts`: Registration endpoint — add token generation and return it in the response
- Google Sheets integration already working — add columns for `payment_token`, `payment_status`, `paid_amount`, `paid_at`

### Established Patterns
- CSS Modules with camelCase class names — WhyDonate widget may need a wrapper with custom styles
- Backend uses Hono framework with typed config from env vars
- Frontend is `'use client'` for interactive components (ConfirmationPanel will need this for widget embedding)
- Error handling pattern: try/catch with graceful degradation

### Integration Points
- New backend endpoint: `POST /api/register/confirm-payment` (validates token, updates Sheets)
- Modified backend endpoint: `POST /api/register` (generates payment token, returns WhyDonate config instead of monobankJarUrl)
- Modified frontend: `ConfirmationPanel` embeds WhyDonate widget with locked amount + redirect URL containing token
- New frontend route handler: detect `?token=...&pid=...` query params on register page → call confirm-payment endpoint → show confirmed state
- New env vars: `WHYDONATE_CAMPAIGN_URL` or `WHYDONATE_EMBED_CODE` (replaces `MONOBANK_JAR_URL`)

</code_context>

<specifics>
## Specific Ideas

- WhyDonate widget should be wrapped in a styled container that matches the confirmation panel's design (UA brand colors, consistent spacing)
- The payment-confirmed state should be visually distinct from the initial confirmation (e.g., green checkmark, "Payment received" heading, hide the WhyDonate widget)
- Consider showing a loading spinner while the confirm-payment API call is in flight
- The register page should gracefully handle the case where someone visits with stale/invalid token query params (show registration form normally)

</specifics>

## Deferred Ideas

- **Zapier integration for reconciliation** — Could use Zapier "Donation Paid" triggers to verify payments server-side as a secondary check. Not needed for v1 but could add reliability.
- **WhyDonate widget on fundraiser pages** — Decided (D-13) but implementation is Phase 3 scope.
- **WhyDonate progress widget** — WhyDonate's own campaign widget can show progress. Could be useful as an alternative to the custom dashboard, but Sheets-based approach is simpler and more controllable.
- **Recurring donations** — WhyDonate supports recurring donations. Not in scope for the charity run event but could be useful for European Resolve's general fundraising.

</deferred>
