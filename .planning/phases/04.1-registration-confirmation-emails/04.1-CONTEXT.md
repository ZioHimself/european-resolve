# Phase 04.1: Registration Confirmation Emails - Context

**Gathered:** 2026-07-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Wire up confirmation emails so they actually send in production. The email infrastructure (nodemailer transport, HTML template, 5 locale files, `sendConfirmationEmail()` function) was built during Phase 4 execution but is currently dead code in production because SMTP credentials are not passed to Cloud Run. This phase fixes two gaps: (1) add SMTP env vars to the deploy workflow so registration confirmation emails send, and (2) add a fundraiser confirmation email to the combined `POST /api/fundraiser/register` endpoint which currently creates a registration without sending any email.

</domain>

<decisions>
## Implementation Decisions

### SMTP Deployment
- **D-01:** SMTP credentials (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`) are stored as **GitHub Secrets** and passed to Cloud Run via the `deploy-backend.yml` workflow. No GCP Secret Manager — keep everything in GitHub for simplicity at this project's scale.
- **D-02:** SMTP provider is **mailbox.org** (`smtp.mailbox.org:465`) using the `info@european-resolve.org` mailbox. This is confirmed and already in use for the domain.
- **D-03:** DNS records (SPF/DKIM/DMARC) for `european-resolve.org` are **already configured** — no DNS work needed in this phase.

### Email Templates
- **D-04:** Two separate email templates:
  1. **Registration confirmation** (already built) — sent from `POST /api/register` for Track A (registration-only) participants. Contains participant ID, tier, rewards, WhyDonate donation CTA, event details.
  2. **Fundraiser confirmation** (new) — sent from `POST /api/fundraiser/register` for Track B (fundraiser+registration) participants. Contains BOTH registration details (participant ID, tier, rewards, donation CTA) AND fundraiser details (fundraiser page URL, edit link).
- **D-05:** The standalone `POST /api/fundraiser` endpoint is not used by the frontend — all fundraiser creation goes through the combined `POST /api/fundraiser/register` flow. No email needed for the standalone endpoint.

### Fundraiser Confirmation Email
- **D-06:** The fundraiser confirmation email includes the **full registration confirmation** (same details: participant ID, tier, amount, rewards, donation CTA) plus an additional section with:
  - Fundraiser page URL (shareable link)
  - Edit link (with edit token) so the fundraiser creator can update their page
  - Fundraiser display name and goal
- **D-07:** Fundraiser confirmation email is localized using the same `EmailLocale` pattern — extend the type and all 5 locale files (en, fr, uk, nl, de) with fundraiser-specific strings.

### Claude's Discretion
- Fundraiser email HTML template layout and visual design (consistent with existing registration email UA branding)
- How to structure the edit link URL (query param vs path-based token)
- Whether to extract shared email sections (header, footer, registration details table) into reusable partials or keep templates self-contained
- Exact fundraiser-specific locale string keys and copy

</decisions>

## Existing Code Insights

### Reusable Assets
- `backend/src/email/render.ts`: Full HTML email renderer with UA branding (blue header, gold accent, paper background). Extend with a `renderFundraiserEmail()` function alongside existing `renderConfirmationEmail()`.
- `backend/src/email/locales/`: All 5 locale files already have registration confirmation strings. Extend `EmailLocale` interface for fundraiser-specific fields.

- `interpolate()` and `escapeHtml()` utilities in `render.ts` — reusable for new template.

### Established Patterns
- Fire-and-forget email sending: `.catch((err) => console.error(...))` — email failures don't block the API response
- Locale resolution via `LANGUAGE_TO_LOCALE` mapping in `types.ts`
- HTML email built as template literal with inline styles (no CSS — email client compatibility)
- Email data interface (`RegistrationEmailData`) defines what the template needs

### Integration Points
- `deploy-backend.yml`: Add `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` to Cloud Run env_vars (via `${{ secrets.* }}`)
- `fundraiser.ts` line ~362: Add `sendFundraiserEmail()` call before the return statement (same fire-and-forget pattern as `register.ts`)
- `EmailLocale` interface: Extend with fundraiser-specific fields (page URL label, edit link label, etc.)

<specifics>
## Specific Ideas

- The fundraiser confirmation email should feel like a complete "welcome" email for Track B participants — they've both registered AND created a fundraiser page, so it should celebrate both actions
- The edit link in the email is important — it's the only way fundraiser creators can access their page editor (no user accounts)
- Keep the same visual style as the existing registration email (UA blue/gold header, paper background, consistent typography)

</specifics>
