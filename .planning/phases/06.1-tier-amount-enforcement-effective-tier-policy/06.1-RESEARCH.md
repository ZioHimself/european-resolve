## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** When amount < selected tier price and the donor clicks Next on step 1, show an **inline error inside the WhyDonate shadow DOM** near the amount field — hook step-1 validation the same way WhyDonate shows native min-donation messages. Do not use an external overlay banner as the primary feedback.
- **D-02:** **Fix amount only** — the donor must raise the amount to meet the minimum. No inline tier downgrade links or tier picker on the payment step. The existing Start Over flow remains available elsewhere but is not promoted in the gate error.
- **D-03:** **Firm, factual error copy:** "Minimum donation for {tierName} is €{price}. Please enter at least this amount to continue."
- **D-04:** Gate applies to **registration payment flows only** — Track A registration confirmation and Track B fundraise registration confirmation (both involve tier selection). **No gate** on fundraiser page visitor donations, donor wall donations, or other standalone donate CTAs.
- **D-05:** **Donor wall donations have no minimum** — unrestricted amounts; gate logic must not run on those embeds.
- **D-06:** **Pre-fill** the WhyDonate `other-amount-number` field with the selected tier price on widget load (revises Phase 6 D-16 for registration flows). Donor may edit upward freely; gate blocks advancing below the minimum.
- **D-07:** **No overpay hint** before payment — do not advertise that higher amounts unlock additional tiers. Copy states the minimum only; tier cards during registration already communicated tier structure.
- **D-08:** **Same pre-fill behavior** for Track A and Track B registration confirmation panels.
- **D-09:** Write the pre-filled tier price to `sessionStorage` (`r4u:donation-amount`) **immediately on load**, not only after donor edit. Input/change events continue to update the stash if the donor changes the amount before redirect (iDEAL/PayPal).
- **D-10:** After payment, confirmation panel shows **effective tier only** — tier name and rewards earned from amount paid. Do not show originally selected tier or an explicit "upgrade" callout when effective > selected.
- **D-11:** Payment confirmation email **matches on-page** — effective tier name + cumulative rewards only; no selected-vs-effective comparison.
- **D-12:** **Merged cumulative rewards list** — single bullet list combining rewards from all tiers up to and including the effective tier (additive model per ADR-009).
- **D-13:** If the client gate is bypassed (devtools) and amount < selected tier price, **confirm silently** with downgraded effective tier and merged rewards for that amount. Do not reject confirm-payment or show a downgrade warning in normal UX.
- **D-14:** Introduce tier_id **`donor`** for payments **below €10** (below Supporter threshold): record as paid with amount, assign donor-tier thank-you only (no runner rewards). Effective tier logic must handle this floor tier.

### Policy Locked by ADR-009 (not re-decided here)
- Step 1 client gate + backend `getEffectiveTier(observedAmount)` on confirm-payment
- Five tier thresholds: €10 / €15 / €30 / €60 / €100
- Registration row keeps **selected tier** as intent; effective tier drives rewards and payment email only
- Record `paid_amount` from observed amount only; never backfill from registered tier price
- Two-email model: registration = target tier + payment ask; payment = effective tier + rewards
- Redirect payments: sessionStorage stash before redirect, `parseWhyDonatePaymentReturn()` on return
- Out of scope: unique participant dedup, top-up as primary UX, Stripe iframe validation

## Summary

Phase 06.1 adds a **registration-only step-1 minimum gate** to the existing WhyDonate widget integration and makes the **backend authoritative** for effective tier and cumulative rewards at `confirm-payment`. Production analysis of `wp_styling.js` [VERIFIED: local file `/Users/serhiy/downloads/wp_styling.js`] confirms the hook surface: step-one Next uses `.wd-part-step-one-next`, validates via closure-scoped `validateTotalAmount()`, advances with `setDonationStep(id, 2)`, and shows errors in `#donation-amount-error-${id}`. The Stripe payment portal (`#step-three-portal-${id}`) is appended to **document light DOM**, not the shadow root — irrelevant for step-1 gating but important so planners do not search the shadow tree for Stripe.

The codebase gap is clear: `sheets.ts` lines 240–242 still return **registered-tier** rewards; `getEffectiveTier()` does not exist; `WhyDonateWidget.tsx` has no gate or tier-price pre-fill; post-payment UI (`ConfirmationPanel.tsx` confirmed branch) displays **registration** `result.tierName` / `result.rewards` instead of the `confirm-payment` API response.

**Primary recommendation:** Add optional `minTierAmount` / `minTierName` props to `WhyDonateWidget` (passed only from `ConfirmationPanel` and `FundraiserConfirmation`). Attach a **capture-phase click listener** on `.wd-part-step-one-next` that blocks advance when base amount `< minTierAmount`, reusing `#donation-amount-error-${id}` for inline error display. Implement `getEffectiveTier()` + `getCumulativeRewards()` in `backend/src/tiers.ts` and call from `confirmPayment()`. Store effective tier from API response in confirmation panel state for post-payment display.

## Hook Implementation Options

Analysis based on `wp_styling.js` lines 635–674 (button creation + onclick), 2682–2705 (`validateTotalAmount`), 1750–1802 (`setDonationStep`), 2057–2097 (`ensureStepThreePortal`). [VERIFIED: local wp_styling.js grep/read]

### Option A: Capture-phase click listener on `.wd-part-step-one-next` (RECOMMENDED)

**What:** After shadow root is available, `querySelector('.wd-part-step-one-next')` and `addEventListener('click', handler, true)`. In handler: read base amount from `#other-amount-number-${id}`; if `< minTierAmount`, `preventDefault()` + `stopImmediatePropagation()`, write error to `#donation-amount-error-${id}` (same element WhyDonate uses), return false. On valid amount, clear/hide error and allow native handler to run.

**Why it works:** WhyDonate assigns `donateButton.onclick = () => {...}` (target-phase). Capture listeners run first; `stopImmediatePropagation()` prevents the property handler from firing. [VERIFIED: wp_styling.js:659–674]

**Pros:** No script injection; survives minor WhyDonate updates if class/ID contract holds; matches D-01 inline error pattern.

**Cons:** Fragile if WhyDonate switches to `addEventListener` with capture + stopPropagation; must attach after button exists (poll/MutationObserver retry like pre-fill).

**Confidence:** HIGH

### Option B: Replace/wrap `button.onclick`

**What:** Save `const original = btn.onclick; btn.onclick = (e) => { if (!passesTierGate()) return; original?.call(btn, e); }`

**Pros:** Explicit control order.

**Cons:** WhyDonate owns the property; any re-init overwrites wrapper. Harder to clean up on unmount.

**Confidence:** MEDIUM — viable fallback if capture phase behaves unexpectedly in tests.

### Option C: Wrap `validateTotalAmount()`

**What:** Intercept native min/max validation to also check tier minimum.

**Verdict:** **NOT VIABLE.** `validateTotalAmount` is defined inside the widget IIFE closure (line 2682), not exposed on `window` or the shadow root. Cannot wrap without loading a modified script. [VERIFIED: wp_styling.js structure]

**Confidence:** HIGH (negative claim)

### Option D: MutationObserver on step change (block step 2)

**What:** Watch `#step-two-container-${id}` becoming visible; revert if amount too low.

**Verdict:** **REJECT.** Step transition already happened; `setDonationStep` is also closure-scoped. Would flash step 2 briefly and fight WhyDonate internal state.

**Confidence:** HIGH (negative claim)

### `getEffectiveTier(observedAmount: number): TierId`

Backend-authoritative in `backend/src/tiers.ts`:

```typescript
const TIER_THRESHOLDS: { id: TierId; min: number }[] = [
  { id: "ultramarathoner", min: 100 },
  { id: "marathoner", min: 60 },
  { id: "relay-runner", min: 30 },
  { id: "sprinter", min: 15 },
  { id: "supporter", min: 10 },
  { id: "donor", min: 0 },
];

export function getEffectiveTier(amountEur: number): TierId {
  if (!Number.isFinite(amountEur) || amountEur <= 0) return "donor";
  for (const { id, min } of TIER_THRESHOLDS) {
    if (amountEur >= min) return id;
  }
  return "donor";
}
```

Sort descending by `min` so first match is highest tier reached. [CITED: ADR-009 thresholds; verified against `src/data/event.ts` and `backend/src/tiers.ts` prices]

### Cumulative rewards merge

**Additive model (D-12):** For effective tier ≥ `supporter`, merge reward strings from every tier from `supporter` through effective tier, deduplicated, order preserved (lowest tier first).

```typescript
const REWARD_TIER_ORDER: TierId[] = [
  "supporter", "sprinter", "relay-runner", "marathoner", "ultramarathoner",
];

export function getCumulativeRewards(tierId: TierId, language: string): string[] {
  if (tierId === "donor") {
    return getLocalizedRewards("donor", language); // single thank-you string
  }
  const seen = new Set<string>();
  const merged: string[] = [];
  for (const id of REWARD_TIER_ORDER) {
    for (const item of getLocalizedRewards(id, language)) {
      if (!seen.has(item)) {
        seen.add(item);
        merged.push(item);
      }
    }
    if (id === tierId) break;
  }
  return merged;
}
```

**Note:** `getLocalizedRewards` splits `tierRewards` on `" · "` ([VERIFIED: `backend/src/tiers.ts:36`]). Per-tier strings in `en.ts` are already cumulative-ish in wording; dedupe prevents duplicate bullets when merging.

## Common Pitfalls

### Pitfall 1: Gate listener attaches before step-one button exists
**What goes wrong:** Next click unguarded on first interaction.
**How to avoid:** Retry attachment in existing MutationObserver callback (same pattern as donor pre-fill retry).
**Warning signs:** Under-minimum amount reaches step 2 in manual QA.

### Pitfall 2: Tip included in tier gate comparison
**What goes wrong:** Donor enters €9 + tip passes gate incorrectly or €10 base fails incorrectly.
**How to avoid:** Compare `readAmount()` (base input only), not `getTotalAmount`.
**Warning signs:** Discrepancy vs Stripe charge amount.

### Pitfall 3: Post-payment UI shows registered tier
**What goes wrong:** Overpayer sees selected tier rewards, not earned rewards (violates D-10).
**How to avoid:** Persist `confirm-payment` response fields in confirmation panel state.
**Warning signs:** €100 payment after €15 registration still shows Sprinter rewards only.

### Pitfall 4: Step-three portal assumed inside shadow DOM
**What goes wrong:** Planner/tasks search shadow tree for Stripe; integration tests mock wrong DOM.
**How to avoid:** Document light DOM portal; step 3 validation explicitly out of scope (ADR-009).
**Warning signs:** Test helpers only create shadow content, miss portal behavior.

### Pitfall 5: wp_styling.js DOM contract change
**What goes wrong:** Class `.wd-part-step-one-next` or error ID renamed; gate silently stops working.
**How to avoid:** Widget tests assert listener attachment; manual smoke on production script after WhyDonate updates.
**Warning signs:** `querySelector` returns null; gate tests pass on mock DOM but fail in staging.

### Pitfall 6: `donor` tier added to registration validation
**What goes wrong:** Users could register as "donor" without runner commitment.
**How to avoid:** Keep `donor` out of `VALID_TIER_IDS` on register routes; payment-only tier.

## Code Examples

### Capture-phase gate (recommended)

```typescript
// Source: DOM event model + wp_styling.js:659-674 (onclick handler)
function attachTierAmountGate(
  shadow: ShadowRoot,
  id: string,
  minAmount: number,
  tierName: string,
  errorCopy: (tierName: string, price: number) => string,
): () => void {
  const btn = shadow.querySelector(".wd-part-step-one-next");
  const errorEl = shadow.getElementById(`donation-amount-error-${id}`);
  if (!btn || !errorEl) return () => {};

  const handler = (event: Event) => {
    const amount = readAmount(shadow, id);
    if (amount < minAmount) {
      event.preventDefault();
      event.stopImmediatePropagation();
      errorEl.style.display = "block";
      errorEl.style.visibility = "visible";
      errorEl.innerText = errorCopy(tierName, minAmount);
      return;
    }
    errorEl.style.display = "none";
    errorEl.style.visibility = "hidden";
  };

  btn.addEventListener("click", handler, true);
  return () => btn.removeEventListener("click", handler, true);
}
```
