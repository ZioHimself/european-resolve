# Phase 06.1: Tier amount enforcement & effective-tier policy - Context

**Gathered:** 2026-08-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Enforce tier-amount policy for registration payment flows: block WhyDonate step-1 advance when amount is below the selected tier minimum, pre-fill the widget with the tier price, compute effective tier and cumulative rewards from the observed payment amount on confirm-payment, and align confirmation UI and payment email with the effective tier (not the registration selection). Donor wall and other non-registration widget embeds remain unrestricted.

Core policy is locked in ADR-009. This phase implements it plus the UX/copy decisions captured below.

</domain>

<decisions>
## Implementation Decisions

### Under-Minimum Gate UX
- **D-01:** When amount < selected tier price and the donor clicks Next on step 1, show an **inline error inside the WhyDonate shadow DOM** near the amount field — hook step-1 validation the same way WhyDonate shows native min-donation messages. Do not use an external overlay banner as the primary feedback.
- **D-02:** **Fix amount only** — the donor must raise the amount to meet the minimum. No inline tier downgrade links or tier picker on the payment step. The existing Start Over flow remains available elsewhere but is not promoted in the gate error.
- **D-03:** **Firm, factual error copy:** "Minimum donation for {tierName} is €{price}. Please enter at least this amount to continue."
- **D-04:** Gate applies to **registration payment flows only** — Track A registration confirmation and Track B fundraise registration confirmation (both involve tier selection). **No gate** on fundraiser page visitor donations, donor wall donations, or other standalone donate CTAs.
- **D-05:** **Donor wall donations have no minimum** — unrestricted amounts; gate logic must not run on those embeds.

### Widget Amount Default
- **D-06:** **Pre-fill** the WhyDonate `other-amount-number` field with the selected tier price on widget load (revises Phase 6 D-16 for registration flows). Donor may edit upward freely; gate blocks advancing below the minimum.
- **D-07:** **No overpay hint** before payment — do not advertise that higher amounts unlock additional tiers. Copy states the minimum only; tier cards during registration already communicated tier structure.
- **D-08:** **Same pre-fill behavior** for Track A and Track B registration confirmation panels.
- **D-09:** Write the pre-filled tier price to `sessionStorage` (`r4u:donation-amount`) **immediately on load**, not only after donor edit. Input/change events continue to update the stash if the donor changes the amount before redirect (iDEAL/PayPal).

### Effective Tier, Rewards & Messaging
- **D-10:** After payment, confirmation panel shows **effective tier only** — tier name and rewards earned from amount paid. Do not show originally selected tier or an explicit "upgrade" callout when effective > selected.
- **D-11:** Payment confirmation email **matches on-page** — effective tier name + cumulative rewards only; no selected-vs-effective comparison.
- **D-12:** **Merged cumulative rewards list** — single bullet list combining rewards from all tiers up to and including the effective tier (additive model per ADR-009).
- **D-13:** If the client gate is bypassed (devtools) and amount < selected tier price, **confirm silently** with downgraded effective tier and merged rewards for that amount. Do not reject confirm-payment or show a downgrade warning in normal UX.
- **D-14:** Introduce tier_id **`donor`** for payments **below €10** (below Supporter threshold): record as paid with amount, assign donor-tier thank-you only (no runner rewards). Effective tier logic must handle this floor tier.

### Policy Locked by ADR-009 (not re-decided here)
- Step 1 client gate + backend `getEffectiveTier(observedAmount)` on confirm-payment
- Five tier thresholds: €10 / €15 / €30 / €60 / €100
- Registration row keeps **selected tier** as intent; effective tier drives rewards and payment email only
- Record `paid_amount` from observed amount only; never backfill from registered tier price
- Two-email model: registration = target tier + payment ask; payment = effective tier + rewards
- Redirect payments: sessionStorage stash before redirect, `parseWhyDonatePaymentReturn()` on return
- Out of scope: unique participant dedup, top-up as primary UX, Stripe iframe validation

### Claude's Discretion
- Shadow DOM hook implementation (intercept Next button, wrap `validateTotalAmount()`, error element placement)
- Exact `donor` tier reward strings in locale files and email templates
- `getEffectiveTier()` and cumulative reward merge implementation (shared module vs backend-authoritative)
- Pre-payment confirmation panel copy tweaks (registration email already has `rewardsDisclaimer`; user did not discuss pre-payment rewards framing)
- Gate detection: how to distinguish registration widget instances from donor-wall embeds in code

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `WhyDonateWidget.tsx`: Already reads amount from shadow DOM, persists to sessionStorage on input/change, pre-fills donor fields, MutationObserver for step-four payment success.
- `whydonatePaymentRedirect.ts`: `PAYMENT_AMOUNT_STORAGE_KEY` and `parseWhyDonatePaymentReturn()` for iDEAL/PayPal redirect returns.
- `backend/src/tiers.ts`: Central tier prices and localized reward strings — extend with `getEffectiveTier()` and `donor` tier.
- `ConfirmationPanel.tsx` / `FundraiserConfirmation.tsx`: Post-payment UI already displays tier name, amount, and rewards from API response — will consume effective tier once backend changes.

### Established Patterns
- `'use client'` for widget and confirmation components.
- Never substitute registered tier price for observed amount (`sheets.ts` comment at confirmPayment).
- Registration email already includes `rewardsDisclaimer: "Final rewards are based on your donation amount."`
- Tier prices duplicated in `src/data/event.ts` and `backend/src/tiers.ts` — effective tier logic should share thresholds.

### Integration Points
- Step-1 gate: shadow root elements `other-amount-number-{id}`, step-one next button, optional `validateTotalAmount()` in WhyDonate's `wp_styling.js`.
- Gate scope: pass selected tier price into `WhyDonateWidget` only from registration confirmation panels, not from `FundraiserPage` visitor donate or donor wall embeds.
- `confirmPayment` response fields `tierName`, `rewards`, `amountEur` must reflect effective tier and cumulative rewards.
- New `donor` tier_id for sub-€10 payments: Sheets column tier (col H), email locale `tierRewards`, API response.

### Current Gap (pre-06.1)
- `sheets.ts` lines 240–242: tier rewards come from **registered** tier, not observed amount — must change.
- No step-1 minimum gate in `WhyDonateWidget.tsx`.
- No `getEffectiveTier()` function in codebase.
- Amount field not pre-filled with tier price (Phase 6 D-16).

</code_context>

<specifics>
## Specific Ideas

- Gate error tone: firm and factual, not friendly/nudging.
- Donor wall is explicitly exempt from any minimum — important operational distinction.
- Sub-€10 payments get a `donor` tier_id rather than blank tier or supporter rewards.
- No marketing of overpay upgrades — keep payment step focused on meeting the selected tier minimum.

</specifics>

<deferred>
## Deferred Ideas

- **Pre-payment rewards framing on confirmation panel** — user skipped this area; registration email disclaimer may suffice. Revisit if pre-payment UI still implies guaranteed selected-tier rewards.
- **Unique participant counting** — distinct emails with paid status (ADR-009 follow-up, separate phase).
- **Top-up flow** — supplementary payment if gate bypassed (ADR-009 fallback only, not primary UX).
- **Inline tier downgrade on gate error** — user chose fix-amount-only path.
